# QA Swarm — ядро и память контекста

Дата: 2026-08-13  
Статус: черновик на ревью  
Область: только подпроект 1 (ядро swarm + память). Остальные контуры — отдельные spec.

## 1. Зачем

Нужна команда агентов в Cursor, которая знает продукт снаружи репозитория `qaswarm`: умеет по команде построить карту системы, запомнить её в git и отвечать на вопросы из этой памяти, ходя во внешние источники только при пробеле или устаревании.

Этот spec задаёт фундамент. Анализ требований, тест-документация, проверка поведения, тикеты, API/e2e-тесты и верификация багов **не входят в v1**. Они позже читают ту же память, не дублируя её.

## 2. Цели v1

- Человек работает только с координатором в workspace `qaswarm`.
- По команде «запомни систему» охотник строит **карту** (каталог публичного API + краткие карточки + пробелы), библиотекарь записывает её в git.
- Координатор отвечает на вопросы о продукте **из файлов памяти**, с указанием источника и даты.
- Внешний вызов (API/MCP) только если карточки нет, она `stale`, или пользователь явно просит обновить.
- Секреты не попадают в git и в текст карточек.

Критерий готовности: три приёмочных сценария в разделе 12 проходят на реальном публичном API продукта.

## 3. Вне скоупа v1

- Генерация тест-планов, кейсов, чек-листов.
- Систематическая проверка UI/поведения (контур MCP-verification). Browser MCP в v1 — только точечный добор при `recall`/`refresh`, не стартовый обход экранов.
- Создание и ведение задач в трекере.
- Покрытие API/e2e-тестами.
- Проверка багов.
- Векторный поиск / RAG (допустим позже поверх тех же файлов).
- Полный снимок всех полей и записей API.
- Несколько продуктов одновременно (схема путей уже с `product-id`, но v1 настраивает один).
- Параллельные Hunter на один продукт.
- Автообновление по расписанию (Cursor Automations).

## 4. Зафиксированные решения

| Тема | Решение |
|------|---------|
| Где работает | Cursor: главный агент + skills + субагенты |
| Где лежит swarm | Отдельный репозиторий `qaswarm`; продукт снаружи |
| Источники | Лестница: public API → internal API (если есть в конфиге) → browser MCP только если API не отвечает |
| Память | Markdown + JSON в git; RAG не в v1 |
| Роли | Координатор, Hunter, Librarian |
| Стартовый проход | Карта, не дамп; углубление (`deep`) позже или точечно по вопросу |
| Оркестрация | Субагенты; шина — файлы на диске |
| Продуктов в v1 | Один, пути готовы к нескольким |

## 5. Архитектура

`qaswarm` — Cursor workspace. В нём живут правила агентов, skills, конфиг подключения продукта и память. Код продукта сюда не копируется.

Человек всегда пишет координатору. Координатор:

1. Читает `products/<product-id>/config.yaml` и файлы в `memory/<product-id>/`.
2. Если ответа достаточно и карточка не `stale` — отвечает, субагентов не запускает.
3. Иначе ставит письменную задачу Hunter и/или Librarian. Субагенты не видят чат; в задаче должны быть: `product-id`, цель, разрешённые каналы, что уже есть в памяти, чего не хватает.
4. Считает работу сделанной только когда файлы на диске соответствуют контракту памяти.

Границы:

- Координатор не пишет файлы в `memory/`. Пометку `stale` делает только Librarian.
- Hunter не пишет канонические карточки; только сырьё во входящий черновик.
- Librarian не ходит в продукт; только читает черновик и память, пишет канон.

```text
человек → координатор → [чтение memory]
                      → Hunter → memory/<id>/raw/_incoming/
                      → Librarian → catalog, entities, index, gaps
                      → человек (ответ из канонических файлов)
```

## 6. Структура репозитория

```text
qaswarm/
  AGENTS.md
  .gitignore
  .cursor/
    rules/                 # поведение координатора
    agents/                # промпты Hunter и Librarian
    skills/
      index-system/
      recall/
      refresh/
  products/
    <product-id>/
      config.yaml
      .env                 # gitignore
  memory/
    <product-id>/
      index.md
      gaps.md
      catalog/
        api.md
      entities/
        <slug>.md
      raw/
        _incoming/         # черновик Hunter, не для ответов
        <optional-snapshots>.json
  fixtures/
    demo-catalog/          # эталон карты для сверки схемы
  docs/superpowers/specs/
```

Имена `<product-id>` и `<slug>`: нижний регистр, `a-z0-9-`, без пробелов. Slug стабилен: один смысл — один файл. Переименование только явно командой человека, не эвристикой.

## 7. Подключение продукта

Файл `products/<product-id>/config.yaml` — единственное место, откуда агенты берут «как достучаться до продукта». Хост и токены координатор не угадывает.

Обязательные поля:

- `id` — совпадает с именем каталога
- `name` — человекочитаемое имя
- `public_api.base_url` — база публичного API
- `public_api.catalog_hint` — путь к каталогу относительно `base_url` (OpenAPI/Swagger или discovery). Если `unknown`, Hunter пробует только `/openapi.json`, `/swagger.json`, `/swagger/v1/swagger.json`, `/api-docs` и фиксирует неудачу в `gaps.md`. Ресурсы из головы не выдумывает.

Необязательные:

- `internal_api.base_url` — если поля нет, ступень internal запрещена
- `mcp.browser` — `true`/`false`; по умолчанию `false` для `index-system`; для `recall`/`refresh` браузер разрешён только при `true`
- `ttl_hours` — через сколько часов карточка `map`/`deep` считается `stale` при чтении; по умолчанию `168` (7 суток). `stale` не ставится автоматически фоном: координатор сравнивает `fetched_at` с `ttl_hours` в момент `recall`

Секреты: `products/<product-id>/.env` и/или конфиг MCP в Cursor. Имена переменных в `config.yaml` можно ссылать (`token_env: PUBLIC_API_TOKEN`), значения — никогда.

Если конфига нет, координатор спрашивает минимальный набор (`id`, `public_api.base_url`, есть ли internal, нужен ли browser) и предлагает человеку создать файлы. Сам не выдумывает URL.

В v1 в `products/` ровно один `product-id`. Координатор берёт его без вопроса. Ноль каталогов — стоп и просьба создать конфиг. Больше одного — стоп и вопрос, какой id, даже если это выходит за целевой скоуп.

Hunter ходит в public/internal API инструментами Cursor (HTTP и/или MCP из конфига Cursor). Отдельный HTTP-клиент в репозитории запрещён, кроме GET внутри `tools/upservice_mcp/` для MCP-тула `get_task`.

## 8. Контракт памяти

Канон для ответов человеку: `index.md`, `catalog/api.md`, `entities/*.md`, `gaps.md`.  
`raw/` — доказательная база для Librarian, координатор оттуда не цитирует.

### 8.1. `index.md`

Карта продукта: список доменов и сущностей со ссылками на карточки, датой последнего успешного `index-system`, кратким статусом (`map` / `deep` / `stale`). Без секретов и без сырых JSON.

### 8.2. `catalog/api.md`

Таблица или список: ресурс, HTTP-методы если известны, канал (`public` / `internal`), ссылка на сущность если сопоставлена, `fetched_at`. Только то, что реально вернул API (или его описание). Нет догадок «наверняка есть CRUD».

### 8.3. Карточка `entities/<slug>.md`

Обязательные поля в YAML frontmatter:

- `slug`
- `title`
- `status`: ровно одно из `map` | `deep` | `stale`
- `source`: ровно одно из `public` | `internal` | `browser` (канал, из которого взято **текущее** содержимое)
- `fetched_at`: ISO-8601 с часовым поясом (например `2026-08-13T17:00:00+03:00`)
- `product`: `product-id`

Тело:

- Кратко что это (1–5 предложений)
- Ключевые поля — только если источник их отдал; на статусе `map` можно оставить «поля не детализированы»
- Связи с другими slug, только если видны из источника
- Чего не хватает (локальные пробелы)

Карточка без `source` или `fetched_at` невалидна; Librarian обязан отвергнуть, координатор не имеет права отвечать по ней как по факту.

`status`:

- `map` — появилась из стартовой карты, без целевого углубления
- `deep` — после точечного добора по вопросу или `refresh`
- `stale` — только явная пометка Librarian перед `refresh` (карточка в процессе обновления). Истёкший TTL **не** записывается в frontmatter сам собой.

TTL: если при `recall` `now - fetched_at > ttl_hours`, карточка не считается свежим фактом. Координатор запускает тот же добор, что при промахе. Если канал недоступен — отвечает, что в памяти есть только устаревшие данные (`fetched_at`), и что проверить в конфиге; не выдаёт старое как актуальное.

Повторный `index-system` **не** понижает существующие `deep`-карточки до `map` и не затирает их тело. Обновляет каталог, индекс, `map`-карточки новых сущностей и `gaps.md`. Чтобы переписать `deep`, нужен `refresh` этой сущности.

### 8.4. `gaps.md`

Каждая запись: чего не хватает, какой канал уже пробовали, какой следующий канал имеет смысл, код ошибки если был, дата. Browser на стартовой карте не вызывается — только строка вида «каталог/описание пустые, имеет смысл browser или internal».

### 8.5. Входящий черновик Hunter

`memory/<product-id>/raw/_incoming/` — один проход, один набор файлов. Librarian после успешной записи канона удаляет обработанные входящие файлы. Частично скачанный обрывной файл Librarian не берёт (нет маркера завершения прохода).

Маркер завершения: файл `_incoming/MANIFEST.md` со списком положенных файлов. Нет манифеста — проход неуспешен, в индекс не пишем.

## 9. Роли и skills

### Координатор

Главный агент чата (`AGENTS.md` + `.cursor/rules`). Маршрутизирует, читает память, формулирует задачи субагентам, отвечает человеку. Не ходит в продукт «за компанию», если память достаточна.

### Hunter

Субагент. Лестница каналов. На `index-system` — только public, затем internal если public не дал каталог/описания и internal включён. Browser на `index-system` запрещён. На `recall`/`refresh` — один целевой пробел, следующий канал только если предыдущий не ответил. Пишет только в `_incoming/` + `MANIFEST.md`.

### Librarian

Субагент. Единственный писатель канона. Дедупликация по slug (совпадение смысла с уже существующей карточкой — merge в тот же файл, не новый slug). Отвергает файлы без обязательных полей. Вычищает секреты, если они попали в сырьё: в карточке «поле есть, значение скрыто», в git значения нет.

### Skills

- `index-system` — построить или обновить карту по правилам выше
- `recall` — ответить из памяти; при промахе/TTL — Hunter + Librarian, затем ответ из файла
- `refresh` — пометить цель `stale`, добрать, записать, ответить

Имена skills в репозитории совпадают с этими идентификаторами.

## 10. Потоки

### 10.1. Карта (`index-system`)

1. Координатор проверяет конфиг; если нет — стоп и вопросы человеку.
2. Hunter: public API → каталог ресурсов; краткие описания, если методы это дают; иначе один заход в internal при наличии.
3. Hunter пишет сырьё + `MANIFEST.md`.
4. Librarian пишет `catalog/api.md`, новые/обновлённые `map`-карточки, `index.md`, `gaps.md`; не затирает `deep`.
5. Координатор отчитывается: число сущностей, список пробелов, пути к файлам. Формулировка «система запомнена» запрещена, если канон не записан.

### 10.2. Вопрос (`recall`)

1. Поиск по `index.md` и карточкам (Grep/Read).
2. Попадание и не истекший TTL — ответ с `source` и `fetched_at`, файлы не меняются, Hunter не запускается.
3. Промах, TTL, или явный gap — одна задача Hunter с одной целью. Librarian вливает в существующий slug или создаёт новый. При реальном доборе полей/сценария статус становится `deep`.
4. Ответ только после канона на диске.

### 10.3. Обновление (`refresh`)

Librarian сначала ставит `stale` на указанные карточки (или на всю карту, если человек сказал «обнови всё»). Дальше как точечный добор. «Обнови всё» в v1 означает повтор каталога + обновление `map`-карточек; `deep` обновляются только если человек перечислил slug или сказал «включая deep».

### 10.4. Параллелизм

На один `product-id` одновременно не больше одного Hunter и одного Librarian. Замок: каталог `raw/_incoming/` не пуст (проход идёт или Librarian ещё не вычистил). Второй Hunter нельзя, пока каталог не пуст. Пустой `_incoming/` после отказа Hunter (координатор зафиксировал ошибку, файлы убраны или их не было) — можно запускать снова.

## 11. Ошибки

| Ситуация | Поведение |
|----------|-----------|
| 401/недоступен public API | Не переходить в browser на карте. Gap + сказать человеку проверить URL/токен/MCP |
| Public пустой, internal нет в конфиге | Карта может быть пустой; честный отчёт; gap «нужен internal или browser» |
| Internal включён, тоже пустой | Gap про browser; browser только на recall/refresh если `mcp.browser: true` |
| Browser выключен, а факт только в UI | Ответ: в памяти нет, browser не разрешён, что включить |
| Секрет в ответе API | Не копировать в память и чат |
| Нет MANIFEST | Канон не обновлять; координатор не утверждает успех |
| Дубль сущности | Merge в существующий slug |
| Обрыв посередине | Уже лежащий канон не откатываем; новый канон из неполного входящего не строим |

## 12. Проверка

Автотестов рантайма Cursor нет. Бар — схема + ручные сценарии. Playwright и пайплайн генерации тестов в этот подпроект не входят.

В `fixtures/demo-catalog/` лежит эталон: входной каталог (как будто `_incoming`) и ожидаемые `index.md`, `catalog/api.md`, 2–3 карточки, `gaps.md`. Librarian и ревьюер сверяют форму, не обязательно байт-в-байт текст описаний.

**Сценарий 1 — карта**  
Цель: стартовый проход даёт карту, не дамп.  
Шаги: заполнить `config.yaml` → команда запомнить систему.  
Ожидание: есть индекс, каталог, короткие карточки `map` с `source` и `fetched_at`; секретов в файлах нет; нет полного дампа записей; координатор перечисляет пробелы.

**Сценарий 2 — ответ из памяти**  
Цель: повторный вопрос не бьёт в продукт.  
Шаги: спросить сущность из карточки.  
Ожидание: ответ с источником и датой; `_incoming` пуст; git-статус памяти без новых канонических правок.

**Сценарий 3 — промах**  
Цель: лестница только при пробеле.  
Шаги: спросить то, чего нет в карте.  
Ожидание: один целевой добор → одна обновлённая/новая карточка → ответ из файла; второго Hunter нет.

Прогон на реальном публичном API. Нарушение схемы карточки — провал сценария, даже если ответ в чате выглядит убедительно.

## 13. Что сознательно отложено

- Гибридный семантический индекс поверх git-памяти.
- Скрипт полной выгрузки OpenAPI.
- Стартовый обход UI.
- Второй продукт в том же workspace.
- Skills следующих контуров (тест-доки, тикеты, e2e, баги) — отдельные spec, читают `memory/`.

## 14. Зависимости реализации (без кода в этом spec)

Реализация после утверждения этого файла: `AGENTS.md`, rules, промпты субагентов, три skill, `.gitignore`, пример `config.yaml`, эталон `fixtures/demo-catalog/`, пустое дерево `memory/` и `products/`. Отдельный сервис, БД и CLI-оркестратор не нужны.

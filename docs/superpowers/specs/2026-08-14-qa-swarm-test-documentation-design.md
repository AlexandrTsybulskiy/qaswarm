# QA Swarm — тест-документация

Дата: 2026-08-14  
Статус: черновик на ревью  
Область: подпроект 3. Опирается на ядро и память (`docs/superpowers/specs/2026-08-13-qa-swarm-kernel-memory-design.md`) и анализ требований (`docs/superpowers/specs/2026-08-13-qa-swarm-requirements-analysis-design.md`). Не заменяет их.

## 1. Зачем

Нужно из готовой карточки требований получить **атомарные тест-кейсы** в git-памяти, чтобы проверка, e2e и выгрузка в TMS (Testmo или аналог) читали файлы, а не чат.

Канон — git. В Upservice и в Testmo этот контур не пишет. Схема кейса сразу мапится на сюит/шаги/ожидание TMS, без вендорных полей в v1.

## 2. Цели v1

- Команда «сделай тест-доки для &lt;id&gt;» даёт канонический сюит в `memory/upservice/testdocs/`.
- Вход: только `requirements/<slug>.md` со `status: ready`. Иначе стоп, анализ сам не запускается.
- Один пункт `## Testable` с `→` = один кейс. Группировка по сценариям не делается.
- Чек-лист — индекс id в порядке текущего Testable, без второго текста шагов.
- Id кейса выдаётся один раз и переживает повторный прогон при том же тексте действия и ожидания.
- Агенты не пишут в Upservice и не вызывают Testmo.

Критерий готовности: три сценария в разделе 11 проходят; `tools/memory_schema.py memory/upservice` возвращает `OK`.

## 3. Вне скоупа v1

- Запись в Testmo / иной TMS (отдельный контур; git остаётся источником правды).
- Запись в задачу Upservice.
- Тест-план как отдельный артефакт (скоуп, платформы, вне скоупа).
- Авторская группировка пунктов в сценарные кейсы.
- Генерация без `ready`-карточки требований (в том числе из чата или только из снимка задачи).
- Автозапуск `analyze-requirement` из этого skill.
- Playwright / e2e, MCP-проверка UI, верификация багов.
- Browser MCP и Figma MCP в этом контуре.
- Пакетный прогон по спринту / всем задачам.

## 4. Зафиксированные решения

| Тема | Решение |
|------|---------|
| Куда писать | Только git-память |
| TMS | Не в v1; поля кейса пригодны к выгрузке позже |
| Вход | `ready` карточка требований; иначе стоп |
| Гранулярность | 1 пункт Testable = 1 кейс |
| Чек-лист | Только упорядоченный список id, не второй канон шагов |
| Кто пишет текст кейса | Новый субагент Scribe |
| Кто ставит id | Python-хелпер merge; входящие id игнорируются |
| Стабильность id | Совпадение `action`+`expected` (trim) → тот же id; иначе новый номер |
| Роли | Координатор + Scribe + Librarian |
| Гранулярность команды | Одна карточка требований за команду |

## 5. Архитектура

Человек говорит с координатором. Skill: `generate-testdocs`.

```text
человек → координатор
       → [если нет ready requirements] стоп, сначала analyze-requirement
       → Scribe → _incoming/testdocs.md + MANIFEST
       → Librarian → testdocs/<slug>.md + testdocs/index.md
       → человек (путь, active/orphan, gap)
```

Границы:

- Scribe не ходит в Upservice, Figma, Testmo; не читает уже лежащие testdocs; не пишет канон и не назначает финальные id.
- Librarian не ходит в продукт и не в TMS; канон + merge id; после записи гоняет схему.
- Координатор не пишет `memory/`.
- Hunter и Analyst в этом контуре не запускаются.

Замок ядра: непустой `memory/<product-id>/raw/_incoming/` — новый проход нельзя.

## 6. Пути и slug

```text
memory/upservice/testdocs/index.md
memory/upservice/testdocs/<slug>.md
```

`<slug>` совпадает со slug карточки требований (`task-<id>` или slug спеки без тикета).

- Один смысл — один файл. Повтор той же задачи — merge в тот же slug, не `task-1842-2`.
- `testdocs/` может отсутствовать: дерево ядра и дерево с одними `requirements/` остаются валидными.
- `testdocs/index.md` не валидируется как карточка сюита. Таблица: Slug, Task, Status, Active, Card.

Черновик Scribe: `memory/upservice/raw/_incoming/testdocs.md` плюс `MANIFEST.md` (список содержит `testdocs.md`). После успеха Librarian удаляет incoming.

## 7. Контракт сюита и кейса

YAML frontmatter сюита, парсер ядра: одна строка `ключ: значение`.

Обязательные поля:

- `slug` — как у требования, `[a-z0-9-]+`
- `title` — как у требования
- `product` — `upservice` в v1
- `task_id` — id или `none`
- `requirement` — slug карточки требований
- `status` — ровно `draft` | `ready` | `stale`
- `fetched_at` — ISO-8601 **с смещением**
- `next_id` — целое ≥ 1, следующий свободный номер кейса

`status`:

- `ready` — есть хотя бы один кейс `active`
- `draft` — разобрать нечего (нет ни одного `action → expected`)
- `stale` — только при явном повторном прогоне (Librarian может пометить перед merge; не фоном)

Id кейса: `tc-<prefix>-<n>`.

- Есть `task_id` (не `none`): `<prefix>` = `task_id` (`tc-5210629-1`)
- Спека без тикета: `<prefix>` = `slug` (`tc-checkout-spec-1`)
- `<n>` — целое без ведущих нулей, начиная с 1
- Номер не переиспользуется, в том числе после `orphan`

Тело:

1. `## Cases` — секции `### tc-<prefix>-<n>`. В каждой, строки `ключ: значение`:
   - `title` — короткая подпись для человека и будущего TMS; не ключ матча
   - `action` — левая часть пункта Testable (дословно)
   - `expected` — правая часть (дословно)
   - `status` — `active` | `orphan`
2. `## Checklist` — только маркеры `- tc-<prefix>-<n>` в порядке текущего Testable. Только `active`. `orphan` здесь нет.
3. `## Gaps` — пункты Testable без `→`; пустая секция допустима, заголовок обязателен
4. Явная строка: в Upservice и Testmo не писали

Секреты не копировать (как в ядре).

Ключ матча: `trim(action)` + `"\n"` + `trim(expected)`. Без смены регистра и без нормализации пунктуации. Правка формулировки = другой ключ. `action` и `expected` — одна строка.

Алгоритм merge выполняется **Python-хелпером** в `tools/` (Librarian его вызывает и записывает результат, номера сам не придумывает). Входящие id Scribe игнорируются.

1. Взять существующие кейсы сюита (если файла ещё нет — пусто), включая `orphan`.
2. Для каждого кейса из incoming (порядок = порядок Testable) найти **ещё не занятое** точное совпадение ключа среди существующих:
   - нашли → тот же id, `status: active`, `title` с incoming; этот существующий кейс больше не матчится в этом прогоне
   - не нашли → id с текущим `next_id`, затем `next_id += 1`, `status: active`
3. Существующий кейс без пары во incoming → `status: orphan`, id сохранить. В чек-лист не ставить.
4. Если ключ `orphan` снова появился во incoming и ещё не занят — тот же id, снова `active`.
5. Два одинаковых пункта Testable в одном прогоне — два кейса (второй не забирает id первого).
6. Чек-лист строится только из шага 2, в этом порядке.
7. `next_id` в frontmatter = max(все когда-либо выданные n, включая orphan) + 1.

Карточка без `fetched_at` / `requirement` / `next_id` невалидна. Координатор не называет тест-доки готовыми, если схема не проходит.

### Incoming

Frontmatter: `slug`, `title`, `product`, `task_id`, `requirement`, `fetched_at`. Без `status` и `next_id`.

Scribe пишет кейсы **без** id. Секции называются `### case`. Поля: `title`, `action`, `expected`. Librarian не доверяет никакому `tc-…` во входящем файле.

## 8. Роли и skill

### Координатор

Проверяет замок `_incoming/` и наличие `ready` требований. Запускает Scribe, затем Librarian. Ответ: путь сюита, число `active`, число `orphan`, gap. Не пишет `memory/`. Не запускает Hunter/Analyst из этого skill.

### Scribe (новое)

Субагент `scribe`. Читает только канон `requirements/<slug>.md`. Для каждого пункта `## Testable`:

- есть `→` — один кейс; режет по **первой** стрелке; `action` и `expected` копирует, не перефразирует; `title` — краткая подпись, не замена шагов
- нет `→` — строка в gap incoming, не кейс

Секцию `## Gaps` карточки требований в кейсы не превращает и не дополняет выдуманными проверками. Не читает `testdocs/`. Пишет только `_incoming/testdocs.md` и участие в `MANIFEST.md`.

### Librarian

Расширение: канонизирует testdoc-черновик в `testdocs/`. Дедуп по slug. Не затирает чужие сюиты. Merge id — только вызов хелпера из раздела 7, не свободная нумерация. После записи — `python`/`py -3 tools/memory_schema.py memory/upservice`.

### Skill `generate-testdocs`

Триггеры: «сделай тест-доки», «тест-кейсы для задачи», «сгенерируй кейсы».

## 9. Поток

1. Резолв продукта. Непустой `_incoming/` — стоп.
2. Найти `memory/<id>/requirements/<slug>.md`. Нет файла или `status` не `ready` — стоп: сказать запустить `analyze-requirement`. Scribe не стартует. Testable из чата не брать.
3. Scribe: только эта карточка → incoming без id.
4. Librarian: merge с `testdocs/<slug>.md` → канон + строка в `testdocs/index.md` → схема.
5. Координатор отчитывается. «Тест-доки готовы» только если файл есть и схема `OK`.

Спека без тикета: тот же поток, `task_id: none`, id вида `tc-<slug>-<n>`.

## 10. Ошибки

| Ситуация | Поведение |
|----------|-----------|
| Нет карточки требований или не `ready` | Стоп, не выдумывать Testable |
| Нет `→` в пункте | Gap, кейс не создавать |
| Нет MANIFEST / нет `testdocs.md` во входящих | Канон testdocs не писать |
| Секрет в тексте | Не копировать |
| Повтор той же задачи | Тот же файл, merge id |
| Пункт переформулировали | Новый id; старый без пары → `orphan` |
| Вернули старую формулировку | Тот же id, снова `active` |
| Testmo / Upservice | Не вызываем, не пишем |

Browser MCP и Figma MCP не используются.

## 11. Проверка

Фикстура `fixtures/demo-testdoc/`: incoming без id, уже лежащий сюит с выданными id, ожидаемый канон (сохранённые id, новый номер, `orphan`, чек-лист только из `active` в порядке incoming). Сверка формы и id, не дословного `title`.

`tools/memory_schema.py` проверяет `testdocs/*.md`, если папка есть. Отсутствие папки — не ошибка. `index.md` как карточка не проверяется.

**Сценарий 1 — ready → сюит**  
Цель: атомарные кейсы из Testable.  
Шаги: команда на задачу с `requirements/task-<id>.md` в `ready`.  
Ожидание: `testdocs/task-<id>.md`, по кейсу на каждый пункт со стрелкой, чек-лист из этих id, схема `OK`; Upservice и Testmo не вызваны.

**Сценарий 2 — нет карточки**  
Цель: контуры не сливаются.  
Шаги: команда без `ready` требований.  
Ожидание: стоп, `_incoming` пуст, файлов testdocs не появилось.

**Сценарий 3 — повтор**  
Цель: стабильные id.  
Шаги: тот же slug ещё раз; во втором прогоне один пункт с тем же текстом, один новый, один изменённый.  
Ожидание: тот же файл; неизменный пункт — старый id; новый — `next_id`; изменённый — новый id плюс `orphan` на старый; чек-лист без `orphan`.

Прогон: `py -3 tools/memory_schema.py memory/upservice` → `OK`.

## 13. Что сознательно отложено

- Клиент TMS: `tc-<prefix>-<n>` позже станет внешним ключом (automation/external id); `title` / `action` / `expected` — название и шаги.
- Пометка testdocs `stale` автоматически, когда требование стало `stale`.
- Отдельный файл на каждый кейс (для v1 один сюит на задачу достаточен для выгрузки).
